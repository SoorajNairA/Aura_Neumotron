## Consequential demonstrated limits

1. **Source provenance is curated metadata, not retrieved numerical evidence.** `EvidenceRecord.curated`, `src/aura/verification/evidence.py:33-38`, hashes title, source URL, publisher, source version and property names; numeric fact values and downloaded bytes are absent. `retrieved_at` is current object-construction time. `catalogue.py:43-62` contains Espressif/Bosch references but also TI driver overview, ST diode category, Adafruit category. `_definition`, `catalogue.py:69-78`, assigns one source ID to every supply/current/dimension fact, using local static `_SPECS` values at `82-133`. `_verify_engineering_plan`, `service.py:267-269` and `289-290`, treats an exact catalogue identity with any non-assumption evidence kind as `source_verified`; it does not fetch those source URLs or extract ratings. This is an identifiable small catalogue with citations, not proof the selected board/module's actual operating ratings or dimensions were verified from a retrieved document. `ResearchAgent`, `adapters/research.py:29-67`, really does web requests, but GitNexus class context shows its importing caller is `infrastructure/tools/execution.py`; the workspace verification service has no connection to it. Research results are title/URL/snippet records, not this evidence/fact pipeline.

   Existing tests: `tests/test_goal8_verification.py:44-47` verifies 64-character hash length and local fact IDs belonging to component evidence IDs. It never verifies fetched bytes or numeric fact traceability. `70-78` proves evidence persistence across SQLite restart. `82-90` proves exact upgrade receives a source label, not source correctness.

2. **Production component replacement can preserve incompatible operating values and promote an assumption.** `LiveModificationPlanner.propose`, `modifications.py:117-119`, dispatches REPLACE_COMPONENT to `_replace`. `_replace`, `264-279`, changes exact ID/version and dimensions but preserves old operating parameters, interfaces and other facts. `verify_modification`, `service.py:360-365`, attaches catalogue source references and unconditionally sets `source_verified`, without distinguishing ENGINEERING_ASSUMPTION or reconciling rating values. Demonstrated on generated irrigation graph: `_replace` chooses `micro-pump-12v`; replacement catalogue range is `[9, 12] V`, retained `parameters.voltage_v` is `5.0`, verification accepts, committed pump is `source_verified` with `evidence-curated-component-assumptions`. This uses the actual production helper with a valid same-family decision, but bypasses provider generation. See `production-replacement-rating-provenance.json`, with exact before/candidate/after graphs, results, decision and source hashes; reproduce using `backend_probes.py`.

3. **The graph verifier silently loses limitations on the actual six generated graph snapshots.** `verify_graph`, `service.py:308-329`, evaluates graph-only rules; many plan-only warnings are absent. `_evaluate_evidence`, `graph_rules.py:284-299`, only checks provided `property_facts`; it does not require that they exist or that property values match Evidence entities or fetched sources. Every captured graph (solar tracker, rover, soil pump, fan, gripper, lead-screw) has zero component property_facts. Fresh verify_graph reports accepted, cross_checked, and zero findings for all six, while each persisted create response says ready_with_limitations. See `actual-six-graph-reverification.json` and `actual_six_graph_reverification.py`. This does not assert the HTTP GET verification view immediately loses stored findings: it establishes the fresh candidate verification path that modifications/What-If use has weaker input semantics. `graph_rules.py:27-41` relies on explicit port records/required_interfaces; generated components carry bare interface names. `_voltage`, `55-66`, expects input/output *_v fields, while most generated defaults are voltage_v/load_voltage_v. `_evaluate_requirements`, `243-259`, checks explicit required_capabilities/control_chain, while semantic planner requirements also use required_roles, required_quantity, required_axes, evaluated in the plan verifier. A graph-only result cannot be interpreted as the entire original plan's engineering claims re-proven.

   Existing tests distinguish this: `tests/test_verification_graph_integrity.py:231-244` uses explicitly supplied property_facts to test estimated/stale/conflict warnings; `247-254` tests an already contradictory custom net survives an unrelated name edit and gets rejected. These tests do not exercise absent property facts or propagation of generated plan limitations. `tests/test_verification_real_world.py:158-168` covers declared insufficient/unknown torque in plan verification; the graph-only verifier does not run that plan rule.

4. **Rover represents one shared motor-driver rail without proving driver adequacy or independent channels.** Actual `four-wheel-rover/graph.json`: one `component-motor-driver:load-output` shares net-power-8e7050862603 with all four motor:power terminals, so a driver-load graph path does exist. Driver max_current_a is 1.2; four motors declare 0.6 A each (2.4 A total). Planner supply chooses 3.4 A using `PlannerService._semantic_plan`, `service.py:169`, and the plan budget at verification `service.py:224-237` checks supply capacity, not driver capacity. Graph budget at `graph_rules.py:146-157` consumes available_current_a on explicit power-output sources; it does not consume driver max_current_a. Generated driver interfaces are bare strings and the load-output role is not recognized as an explicit power_output. Fresh rover graph verification has zero findings. This is evidence of a present abstract switching path and a missing rating/channel proof, not an assertion about fabricated real hardware. See `actual-rover-electrical-topology.json`.

5. **Verifier can approve a candidate differing from what Bridge commits.** `VerificationService._with_authoritative_nets`, `service.py:343-346`, preserves existing graph-owned nets. `verify_modification`, `368-370`, checks a changed relationship graph against those preserved nets. `WorkspaceBridge.commit`, `bridge.py:48`, always rematerializes them; `electrical.py:19-29` deletes previous nets and rebuilds from relationships. Demonstrated: initially valid source output to required load input; remove sole power relationship; candidate modification accepted cross_checked, Bridge commit produces disconnected required input, fresh verification rejects ELEC_REQUIRED_PORT_UNCONNECTED. See `net-verification-commit-mismatch.json` and `backend_probes.py`. Scope is a direct public GraphPatch/verification/Bridge API call; current bounded UI does not directly expose this arbitrary remove-electrical-relationship operation. Keep this separate from the production replacement defect.

6. **Missing facts can look clean; malformed graphs are not uniformly classified as rejected.** `EngineeringGraph.validate`, `model.py:110-120`, validates dimensions only if present; optional absent dimensions can pass. `verify_graph` of project plus unspecified component/no dimensions/no interfaces returns cross_checked with no findings. With dimension value null, `model.py:118` raises TypeError, which `verify_graph`'s ValueError-only catch at service.py:314-317 does not catch. Wrong geometry units (V) are correctly rejected with GRAPH_INVALID. See `failure_probes.json` / `.py`. These are direct graph API probes, not confirmed UI input paths.

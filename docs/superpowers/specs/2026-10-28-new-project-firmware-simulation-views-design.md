# New-project firmware, fault simulation, detailed views and breadboard — design

Date: 2026-10-28 · Branch: `AURA-nemotron_test1` · Deadline: 2026-10-30 17:00 UTC
Scope: roadmap phases 5 (detailed representations) and 6 (simulation with fault injection), generalised
from the fan demo to any new project built through "Design with AURA". Phase 7 (hardware, upload,
serial) is out of scope and comes last.

## Goal

When the user builds a new project, Nemotron understands the idea and clarifies requirements (existing
idea chat), and AURA produces a consistent 3D assembly, wiring/schematic, firmware and simulation from
one Engineering Graph: accurate catalogue dimensions, pin names/numbers, wire endpoints, a breadboard
when appropriate, and every unverified detail flagged.

## Global constraints

- AI proposes; deterministic verification decides. Nemotron never writes C++. It fills a fixed-format
  rule list; AURA generates firmware and simulation from that list; `arduino-cli compile` decides.
- Firmware pins come only from the controller `gpio_map`; wiring, schematic, 3D labels and code read
  the same map. No second copy of pin data.
- Never invent ratings. Dimensions come from the catalogue; the breadboard uses nominal standard
  dimensions labelled "nominal standard size".
- Label every simulation "Behavioral model — same rule as firmware, not running on hardware".
- Unknown or unverified details are shown as "unverified", never hidden. Parts without a detailed model
  render as "Generic proxy".
- The fan demo (`fan_sketch.ino.tmpl`, `fanControl`, its simulation) keeps working unchanged.
- No new Python or npm dependencies. Arduino libraries named in generated sketches are pinned versions.

## Step 1 — Driver firmware + Nemotron rule list

### Supported drivers (by catalogue definition id)

| Definition | Role | Pin kind | Code |
|---|---|---|---|
| `ds18b20-module` | input °C | digital (OneWire) | OneWire@2.3.8 + DallasTemperature@4.0.5, fault = `DEVICE_DISCONNECTED_C` |
| `capacitive-soil-v1` | input % | analog (ADC1) | `analogRead`, 0–100 % by linear map with two calibration constants marked "uncalibrated" |
| `photoresistor-module` | input % | analog (ADC1) | `analogRead`, 0–100 %, "uncalibrated" |
| `pir-hc-sr501` | input bool | digital in | `digitalRead` |
| `push-button` | input bool | digital in | `INPUT_PULLUP`, pressed = LOW, 30 ms debounce |
| `relay-module-5v`, `logic-mosfet-module` | output bool | digital out | `digitalWrite` |
| `led-generic` | output bool | digital out | `digitalWrite` |
| `sg90-servo` | output angle 0–180 | PWM | ESP32Servo@3.2.1 |

Any other part wired to the controller is listed as "No driver yet" in Code view and simulation.
Analog inputs must be allocated ADC1 pins (GPIO 32, 33, 34, 35, 36, 39); input-only pins (34–39) are
never assigned to outputs. This changes the pin allocator for both planning and library adds.

### Rule list (Nemotron output, JSON schema enforced)

```
{"rules":[{"input":"<io id>","when":"above"|"below"|"on"|"off","threshold":number|null,
           "release":number|null,"output":"<io id>","onValue":true|number,"offValue":false|number,
           "minOnSeconds":number|null}], "explanation":"<plain words>"}
```

- IO ids are generated by AURA from the graph (e.g. `soil_1`, `pump_1`) with unit and range, and
  given to Nemotron; any unknown id, out-of-range threshold or value is rejected deterministically.
- Semantics: condition true → `onValue`; release condition (opposite side of `release`, or condition
  false when `release` is null) → `offValue`; otherwise hold (hysteresis). `minOnSeconds` keeps an
  output on at least that long. Rules apply in order; a later rule on the same output wins.
- A sensor fault (disconnected/invalid reading) forces outputs driven by that input to their
  `offValue`, except a fan/cooling output which fails safe ON — stated in the rule explanation.
- The same rule list generates: a C++ `control()` function in the sketch, and a TS evaluator for the
  simulation. Both are tested against one shared truth table.
- Rules are produced when the proposal is built and shown on the proposal card in plain words; approval
  covers them. Without a live model, AURA uses a default rule per input→output pair, labelled
  "Default rule — not generated by the live model".
- Compile: after approval AURA compiles the sketch. On failure the errors go back to Nemotron once with
  a request to fix the rule list; still failing → Code view shows the errors and "Firmware does not
  compile", never a success state.
- Sketch also prints one JSON telemetry line per second with every input and output (for phase 7).

## Step 2 — Simulation with fault injection (phase 6)

- Virtual inputs: slider per analog/°C input (catalogue range), toggle per boolean input.
- Outputs show state; 3D follows: fan/pump spin, LED glow, relay state, servo arm angle.
- Faults per part: sensor disconnected, sensor stuck at value, actuator stalled (commanded on, not
  moving → warning), driver shorted (output forced on → warning).
- Uses the TS evaluator from the rule list. Fan demo keeps its existing `fanControl` simulation.

## Step 3 — Pin labels and highlighting (phase 5)

- ESP32-DevKitC pin table: GPIO number, header label, side/position, plus 3V3, 5V, GND, EN; source
  Espressif DevKitC pinout, cited in code.
- Wiring view and schematic: each wire end labelled `<part> · <pin name> (<GPIO n>)` with polarity
  (+, −, signal). Clicking a wire shows both endpoints in the inspector.
- Selecting a part highlights its wires and connected parts in wiring view and 3D.

## Step 4 — Breadboard

- Catalogue: `breadboard-830`, family `breadboard`, 165.1 × 54.6 × 8.5 mm nominal, 2.54 mm pitch,
  evidence "nominal standard size" (assumption).
- Added automatically on approve when the design is a prototype of plug-in modules and the
  requirements do not ask for a PCB or enclosure; the proposal card says so and lets the user remove it.
- Assembly: breadboard is the base; modules placed on it in rows; the controller straddles the centre
  channel. 3D draws jumper wires from pin to pin, each end labelled.

## Step 5 — Detailed 3D models

Procedural models with catalogue dimensions for: relay module, LED, push button, SG90 servo, PIR,
capacitive soil probe, photoresistor module, generic sensor breakout, breadboard. Realistic models are
no longer limited to the fan workflow; anything unmodelled stays a labelled generic proxy.

## Testing

- pytest: driver/sketch generation per supported part, rule-list validation (unknown ids, ranges),
  C++ control generation, ADC1 allocation, default rules, breadboard rule, compile path with a fake
  arduino-cli plus one real compile when arduino-cli is present.
- vitest: TS rule evaluator against the shared truth table, fault effects, pin table labels.
- Playwright: proposal card shows rules; simulation sliders/toggles/faults; wire endpoint labels;
  highlighting; breadboard toggle; proxy label.
- Live: one Nemotron run of a non-fan idea (plant watering) end to end, reported honestly.
- GitNexus impact before editing existing symbols; detect-changes before each commit.

## Out of scope

Upload, serial monitor, live telemetry (phase 7); I2C/SPI drivers (BME280, VL53L0X, MPU6050, BH1750);
motor drivers; custom PCB layout; calibration of analog sensors on real hardware.
